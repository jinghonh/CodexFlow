以下分工、并发和轻量验证要求优先于仓库技能中的默认组织方式。实施子对话可以使用 implement；审查子对话可以使用 code-review，但覆盖它们默认的强制逐票完整测试、自行结束整张票据、额外拆出多个审查代理等安排。GitHub 状态和下一步派发由主对话统一负责。

3. 获取父规格和当前全部子票的正文、评论、状态、标签、负责人及原生依赖。规格含义冲突交给调查子对话定位，只将确实需要产品决策的问题交给我。

## 三、子对话与并行调度

使用 create_thread 创建侧边栏中的独立 Codex 任务。先通过 list_projects 找到本机这个仓库的实际 projectId。实施任务明确从当前 master 创建工作树，避免项目默认分支指向其他历史分支。使用工具真实支持的 model、thinking 和 target.environment 参数，不编造参数。

实施、调查、集成和审查合计最多同时运行 4 个子对话，排队创建中的任务也占位。子对话不自行继续派生任务或子代理；需要协作时由主对话统一分配。

每个可写任务独占工作树和分支，所有文件操作针对自己的目录。主目录的 master 由主对话独占；每个子对话知道自己不是唯一执行者，不改写其他任务的工作树、提交或分支。

调度循环：

- 找出前置票据已实际合并且完成、规格足够明确的开放代理票据；已被其他人负责的票据先核对状态，不重复认领。
- 优先派发能解除更多后续阻塞的票据。依赖独立且接口清楚的任务尽量并行；只要空位中有可安全执行的任务，就继续派发。
- 涉及共同接口、迁移顺序或同一核心契约的任务，先确定前置契约，再并行消费者；不能仅因处于不同工作树就忽略业务依赖。
- 完成一个任务就重新计算可执行集合。已有候选代码等待合并时，优先补上必要的集成或审查，避免四个位置一直被新实施占满。
- 用 wait_threads 配合游标等待完成或阻塞事件，单次等待不超过 60 秒；避免反复全文读取任务或发送催问。
- 一张票据默认一个实施对话。过大时可分成职责明确的子任务，但仍遵守原票据验收和总并发上限。

创建是异步的；只有 clientThreadId 时，不将它冒充可调用的 threadId。保留实际返回的任务身份。独立任务间不假设有自动父子关系。

## 四、模型分配

只使用以下组合。“最高”是 max，不是 ultra。

| 模型与档位 | 工具参数 | 适用任务 |
| --- | --- | --- |
| GPT-6 Luna 最高 | model=gpt-6-luna, thinking=max | 规则明确的小修改、文档、局部界面、机械调整 |
| GPT-6 Sol 高 | model=gpt-6-sol, thinking=high | 常规功能票据，作为默认实施配置 |
| GPT-6 Sol 极高 | model=gpt-6-sol, thinking=xhigh | 跨层功能、协议适配、状态与缓存逻辑 |
| GPT-6 Astra 低 | model=gpt-6-astra, thinking=low | 要求明确但涉及多个模块的独立审查 |
| GPT-6 Astra 高 | model=gpt-6-astra, thinking=high | 复杂业务冲突、难定位错误、高风险逻辑审查 |
| GPT-6 Astra 最高 | model=gpt-6-astra, thinking=max | 较低档位已有具体失败证据、仍无法解决的少数难题 |

主对话按实际复杂度、不确定性和改动范围选档，在调度记录里写一句理由，不按票据编号永久绑定模型。简单审查可使用 Luna 或 Sol；复杂审查交给 Astra。需要升级时保留已获得的事实、失败原因与复现方式，不盲目从头重做。模型或档位不可用时报告事实，不静默改成未授权的模型。

## 五、实施与验证尺度

逐票开发采用轻量验证：运行相关构建或类型检查，验证主要成功路径；相关代码没有变化且没有新失败时，不重复运行相同检查。不强制每票 TDD，不为简单修改建立大套测试，也不把每个假想异常都扩成测试矩阵。

代码按票据实现，优先直接、清晰的逻辑。只在外部输入、协议、持久化等实际边界保留必要校验，内部使用已经验证的领域类型。避免层层重复检查、静默默认值、猜测性兼容、额外兜底和预防性抽象。规格明确要求的证据有效性、密钥保存、取消状态和迁移行为仍是功能，不得以“少写防御代码”为由删掉。

轻量开发验证不撤销最终验收。性能、人工关系样本、真实 Jev 质量和最终桌面流程仍按发布验收票据执行。测试报告区分“已经实现”“已经验证”“尚未验证”；逐票开发关闭时可明确列出由最终验收票据承接的发布级检查，但不能遗漏本票核心交付或把未验证写成通过。

## 六、独立审查与合并

每份待合并业务代码必须由另一独立对话审查。审查者获得票据、有关规格、固定基线 SHA、候选 SHA 和已执行检查，不继承实施对话的整段上下文。

审查只聚焦影响该票核心功能、主要成功路径或明确规格的实质问题，以及明显的凭据泄露、数据破坏和集成错误。不要扩展为全仓库审计、风格整改或无关重构。可改进但不阻碍功能的建议不阻塞合并。同一候选已有可靠的构建和成功路径结果时，审查者不机械重复执行。

集成到 master 的操作串行执行；其他独立票据的实施可以继续并行。合并顺序：

1. 实施子对话提交完整成果，提供分支、实际基线 SHA、最终 HEAD SHA 和验证结果。
2. 主对话确定本次目标 master SHA。若实施结果已包含该版本，直接成为审查候选；若 master 前进导致需要集成，交给集成子对话在独立工作树形成包含当前 master 的候选提交，业务冲突也由它处理。
3. 独立审查针对准备进入 master 的确切候选提交进行。未通过时交回实施或集成子对话修复，只复查受影响部分；报告必须绑定新的候选 SHA。
4. 主对话只核对报告、提交身份、关键检查和依赖状态。确认 master 仍是审查基线后，以快进方式将已经包含该基线的候选结果合入 master，随后普通推送 origin/master。
5. 如果 master、远程基线或候选内容已变化，先重新形成候选并补充针对变化部分的独立审查，不把旧审查结论直接套在新代码上。
6. 推送成功后，向票据记录交付内容、提交、独立审查结论、已验证及未验证事项，再关闭实际完成的实施票。未经要求不创建 PR；若远程保护规则要求 PR，按实际规则处理，不能绕过。

主对话不额外做一轮源码审查。业务实现、冲突解决和审查发现的修复始终交给对应子对话。

## 七、派发内容与消息纪律

每次派发给子对话的提示至少包含：角色、票据链接、交付目标、明确负责的模块或范围、当前前置条件、工作树与分支约束、已知基线、所需规格、轻量验证要求、完成条件，以及下面的汇报格式。工具创建时尚未返回的路径由子对话在自己的环境核实，不能猜测或改写主目录。

子对话只在“当前分配的任务完成”或“确实无法继续”时向主对话发送结果；不发送开始通知、过程进度、频繁提问或部分发现。能够自行查证的事实自行解决，常规实现选择自行判断。自身对话中工具要求的进度说明不等于向主对话发消息。

默认以最终回复交付，由主对话通过 wait_threads 收取；需要显式发消息时，使用已经确认的主任务 ID 调用 send_message_to_thread，只发一次完成或阻塞结果，避免重复上报。

## 八、持续推进与结束

持续推进所有当前可执行工作。遇到人工样本复核、真实服务凭据、环境授权或模型额度等阻塞时，记录原因并继续其他独立票据；需要我处理时集中说明具体行动，不在聊天或 GitHub 索要明文 API Key。

人工复核票据允许代理准备材料，只有实际人工复核完成后才能标记通过；固定结果或模拟服务不冒充真实 Jev 评估。只剩这些外部条件时，明确报告已完成成果和剩余阻塞，不宣称完整 V1 已完成。

只有最终验收满足规格、所需成果已合入并推送 master 后，才关闭父规格 #11。最终报告给出完成与阻塞票据、master 提交、推送结果、最终验收状态及启动方法。
